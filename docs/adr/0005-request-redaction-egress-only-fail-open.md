# 请求脱敏只覆盖出站字节，且恒 fail-open

iRouter 的「请求脱敏」（对齐参考实现 llm-retry-proxy 的 DLP）只作用于**转发给上游的请求体**，不作用于本机落盘副本；且引擎自身的任何失败一律放行，不阻断用户请求。

两条都是刻意的：

**只覆盖出站。** 脱敏发生在转发前，改写后的 body 才发给上游。本机 `requestDetails` 表里存的完整 `messages` 不因此改变——那是**落盘脱敏**，是另一个独立战场，另立项。二者都做会让日志里存的与发出去的不一致，排障时会误导（"日志明明有明文，为什么上游报没收到"）。代价必须说清：**开了脱敏，本机 SQLite 仍是明文**，UI 文案要写明，不能让用户误以为开了就干净了。

**恒 fail-open。** 引擎出错（规则加载失败、正则异常、解码预算耗尽、请求体不可解析）时放行原请求并记日志，不返回错误。参考实现有 `DLP_FAIL_CLOSED`（默认 false），我们**不移植这个开关**——这是本地单用户网关，一条正则写错就让 agent 整条链路 500 是不可接受的。因此引擎内部每个可能抛出的位置都必须自带 try/catch，调用点不包裹（与 `open-sse/rtk/` 既有 hook 的约定一致：`chatCore.js` 的 hook 调用点没有 try/catch，fail-open 是 hook 自己的责任）。

Status: accepted

Considered Options:
- **只做出站（选定）** / 同时做落盘：见上，一致性优先于"顺手多堵一个洞"
- **fail-open（选定）** / fail-closed（拒绝转发不可解析的请求体）：参考实现默认已是 false；本地网关没有多租户场景，可用性 > 严格性
- **移植 `DLP_FAIL_CLOSED` 开关**：留一个"看起来很安全"的开关，但打开后任何解析边界都会变成故障源，收益不抵复杂度
- **不做请求脱敏**：上游供应商侧的数据处理无法由本机控制，凭据外泄不可逆，需要一个出口

Consequences:
- 出站脱敏与落盘明文**并存**，是已知且接受的边界，不是缺陷。CONTEXT.md 的「出站脱敏 / 落盘脱敏」条目与 UI 文案必须保持这个口径
- 落盘侧的已知洞（`truncateField` 截断时保留前 200 字符 `_preview`，`requestDetailsRepo.js:87-93`）**不在本决策范围内**，随落盘脱敏立项处理
- `enableObservability` 的落盘默认行为（不设 `OBSERVABILITY_ENABLED` 即写库，`requestDetailsRepo.js:31`）同样属落盘议题
- 引擎因此必须是纯函数、零 `@/` 依赖，规则与已知密钥由调用方写入——fail-open 的边界才好测
