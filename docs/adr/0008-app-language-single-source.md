# 应用语言只有一个判定点，权威存储放壳层

「应用语言」（界面的语言）由桌面壳层在启动时判定**一次**，按「显式选择 > 系统语言 > 英文」得出唯一结果，再经注入脚本传给面板；面板不参与判定。用户显式选择的语言以壳层设置文件中的 `locale` 字段为权威，面板 cookie 降级为壳层每次启动注入的派生态。

## 为什么判定点必须在壳层

壳层**先于面板存在**：它要渲染原生菜单，而菜单在窗口创建时建立，此时面板还没加载。面板自身也没有任何独立的系统语言来源——首启时 cookie 为空，网关不读 `Accept-Language`（全仓零命中）。所以壳层是唯一在「首启那一刻」有判定源的一层。

更要紧的是**一致性**：壳层菜单与面板界面共用同一次判定，才不会出现「菜单中文、面板英文」。本变更的起点正是这个形态的用户反馈——安装后首启界面是英文。若两层各自判定，同一个割裂会以别的形式回来。

## 为什么权威存储不在 cookie

优先级链要求区分「用户选过」与「没选过」，这份状态必须存在一个地方。壳层**必须在面板存在之前**读到它，因此它不能是 cookie。cookie 只承担「从壳层传给面板」这一个职责。

由此定下：`localStorage` 那份语言偏好退役（它是 client-only，与 cookie 并存必然漂移），写入语言的接口也退役（服务端只写不读，而 cookie 本就能由客户端直接写——留着就是第二个写入口）。浏览器形态（无壳层）下 cookie 即该形态的本地权威。

Status: accepted

Considered Options:

- **壳层判定 + 注入（选定）** / 面板读 `navigator.language` / 服务端读 `Accept-Language` / 服务端读 cookie
- 面板读 `navigator.language` 被否：在 Linux 上它与壳层的判定**同源**（WebKitGTK 的 `navigator.language` 来自 `g_get_language_names()`，即 `LANGUAGE`/`LC_ALL`/`LANG`），换层不解决根因却各带一份成本；Windows 上另有一条「WebView2 是否尊重系统显示语言」的矛盾实测报告
- 服务端读 `Accept-Language` 被否：网关当前零读取，要新增能力；且 WebKitGTK 文档明说它由 `set_preferred_languages` 决定，与 `navigator.language` 同源
- 服务端读 cookie 被否：首启那次 cookie 还是空的，仍需先写一次；它只能消除「已选过语言后」的首屏闪烁，代价是把 `/dashboard` 从静态预渲染拉成动态渲染
- **cookie 权威（被否）** / 两个存储各自独立（被否）：前者在用户清 cookie 后壳层会显示旧语言，后者接受漂移
- **不支持的语言视为「未选择」（选定）** / 视为「显式选择英文」：后者是原行为，它让「声明支持 34 种语言而实际只有 6 份字典」的缺陷以「静默全英文」的形式呈现

Consequences:

- **不新增 IPC 与权限**：复用既有的设置读写命令与菜单重建通道，`build.rs` 的 `AppManifest::commands` 与 `capabilities/` 一行不动。这是「IPC 面最小化」那条硬约束的直接结果
- 壳层设置文件的字段白名单必须同步扩一项，且该文件现有单测明确钉住「未知键被丢弃」——漏改会导致语言设置写不进去
- 运行中改系统语言**不即时跟随**（重启生效）：壳层本就是启动时算一次并缓存，桌面用户改系统语言后一般也会重启
- 首屏仍会先渲染英文再替换（字典 145 KB，SSR 出英文静态页 → hydrate → fetch → 替换 DOM）。要消除它得让服务端读 cookie，代价与「首启那次仍读不到」使这笔交易不成立——这是**已知取舍，不是疏漏**
- **Linux 首启可能仍回落英文**：GUI 会话若 `LANG=C.UTF-8`，三层（壳层 / 面板 / 服务端）都读不到语言信息。出路不是换判定层，而是用户显式选择一次后由权威存储固化
- 存量 cookie 里若保存着已废弃的语言，行为变为「回落系统语言」而非「显示英文」；不需要迁移脚本
- 降级安全：旧版本读到新增的 `locale` 字段会按未知键丢弃，因此从新版本回退到旧版本不会出错
