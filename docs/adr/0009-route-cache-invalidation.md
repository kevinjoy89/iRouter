# 响应缓存必须随构建身份失效，判据放网关入口

Next 16 的 `.next/server/route-cache` 是一份**不会随构建失效**的持久化响应缓存。我们把「构建身份变了就丢弃它」这一步放在**网关自己的入口**（`custom-server.js` 的 `purgeStaleRouteCache`），而不是只在打包脚本里清；判据是 `.next/BUILD_ID`，戳记写在缓存目录**内部**（`route-cache/.build-id`）。

## 为什么必须有这一步

面板的 HTML 外壳是**预渲染**的，外壳里写死了它那一版构建的 chunk 文件名。缓存一旦跨构建存活，返回的就是旧外壳 + 旧 chunk 名：新加的界面元素压根不进 DOM。用户报的「设置齿轮装了没生效」正是这个形态——`.next/static/chunks/` 里已积累三代 chunk（10-09 / 10-10 / 10-11），旧 chunk 还在盘上，于是浏览器照旧渲染上一版界面，**控制台与网关日志一条报错都没有**。若某次安装顺手清掉了旧 chunk，同一份旧外壳就变成白屏/报错；两种形态同一个根因。

## 为什么不能只靠打包脚本

产物本身是干净的（`tools/build-server.mjs` 先 `rmSync(OUT)` 再复制，并已补产物级守卫禁止 route-cache 进包）。脏的是**安装目录**：把新负载覆盖到旧安装目录时，上一版运行时写下的缓存原样留着。装机路径不止一条——NSIS 覆盖安装、Tauri updater、手工拷贝、开发期直跑——唯一都被经过的一层是网关入口，所以判定放在那里。打包脚本那一步仍然保留：它保证「产物里没有缓存」，让运行时不必去猜一个恰好自带戳记的包。

## 为什么判据是 BUILD_ID

它是每次构建都变的构建身份，而「构建变了」正是缓存变错的**充要条件**。比 mtime 稳（复制会改 mtime 却不改内容，反向也会），比版本号准（同一版本可能重打包）。

戳记位置是关键细节：写在**缓存目录内部**，让戳记与它描述的那份缓存同生共死。这样不存在「戳记是新的、缓存是旧的」这种漏判形态：

- 覆盖安装只替换已知文件 → 戳记仍是旧 BUILD_ID → 不符 → 清缓存（正确）
- 整个 `.next/` 被换掉 → 戳记随旧缓存一起消失 → 视为首次 → 建目录写戳记（正确）

第一版把戳记放在 `.next/` 根下（与缓存分离），**存量安装恰恰没有戳记**——而那正是要修的那批机器，判据会漏掉它们。变异测试钉住了这个差异（把戳记移回缓存目录外，6 条用例立刻变红）。

## 为什么清目录是安全的

缓存是**纯派生态**：清掉只会让 Next 从当前种子重新提升一次，不丢任何用户数据。因此可以无条件清，不需要迁移脚本，也不需要区分「首次安装」与「升级安装」——两者都走同一条路径。

## Status

accepted

## Considered Options

- **网关入口按 BUILD_ID 清（选定）** / 打包脚本清 / 自定义 cacheHandler / 关掉 ISR 落盘
- 打包脚本清被否（单独用）：管不到安装目录里那份存量缓存，而那正是事故现场
- 自定义 `cacheHandler` 被否：为一件「启动时做一次」的事替换掉 Next 整个缓存实现，成本与风险都不成比例
- `experimental.isrFlushToDisk: false` 被否：它只关 `set()` 与 `promoteSeed`，**`get()` 不受它管**，读了照样返回旧条目，不是绕过
- 戳记放 `.next/` 根下被否：与缓存分离，存量安装（无戳记）会漏判——正是要修的那批

## Consequences

- 每次构建后的**首次启动**会多一次目录删除与一次缓存重建；之后每次启动是纯读（只比一次戳记），不损失缓存收益
- **fail-open**：清理失败只留日志、不阻断启动。最坏结果是界面回退到上一版，而不是网关起不来
- 这条守卫是**机制性**的：只要构建身份变了就一定清，不依赖有人记得在发版流程里加一步
- 与「设置入口」那条 spec 的关系：面板内入口本身是对的（`Header.js` 的 `SettingsButton` → `irouter:open-settings` → `ShellSettingsHost`），缺陷只在「新代码没被送到用户面前」。所以修复不碰面板，只修交付链
- 未来若 Next 自己补上跨构建失效（key 里含 BUILD_ID），这段逻辑可以整体删除——它是补偿性的，不是设计偏好
