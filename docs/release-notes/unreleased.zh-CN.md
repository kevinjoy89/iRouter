## Fixes
- **Tray/三平台**: 统一托盘图标并修「深色任务栏上看不到」（用户实机截图：macOS 正常、Win11 深色模式基本看不到、MX Linux 面板上是一团黑）。根因是 `tray.rs` 三平台共用同一张**纯黑 + alpha 的 macOS 模板图**：`icon_as_template` 是 **macOS only**（`tauri tray/mod.rs:295` 文档原文），macOS 会按菜单栏明暗自动反色，所以那边一直对；Windows/Linux **原样绘制**，纯黑图形落在深色任务栏/面板上对比度只有 **1.29:1（Win11 深色 `#202020`）/ 1.66:1（Xfce `#2E3436`）**——等于隐形。现按平台取色：macOS 仍用模板图 + `icon_as_template(true)`；Windows/Linux 用**同一 alpha 轮廓的品牌橙 `#F14B0D`**（应用图标橙色像素中位数，白底 3.65、`#202020` 上 4.46、`#2E3436` 上 3.46，三种底都 ≥3:1）。新增 `assets/tray-color.png` 与两条断言：**可见性**（对三种典型底色算 WCAG 对比度，≥3:1）与**同轮廓**（与模板图逐像素比 alpha，防止只重做一张）。变异验证：橙色图换回纯黑 → 可见性断言红在 `1.29:1`；只改一张的一个像素 → 同轮廓断言红在第 225 像素
- **Linux/打包**: 启动器里显示的是写给开发者的 crate 描述（用户实测 MX Linux 菜单显示「iRouter 桌面壳层（Tauri v2 + Bun sidecar）」）。根因：`.desktop` 的 `Comment` 取自 `bundle.shortDescription`，**不设就回落到 `Cargo.toml` 的 `description`**（tauri-bundler `linux/freedesktop/mod.rs:171`）。现显式设置 `shortDescription: "iRouter 本地智能网关"`，并补 `longDescription`（进 deb 长描述，此前是 `(none)`）；同时把断言加进 CI 的 Linux 包烟测——解包 deb 读 `usr/share/applications/iRouter.desktop`，`Name` / `Comment` 按字面量钉死（只断言"文件在不在"抓不住文案回归）；`bundle.category` 一并补成 `Utility`——此前 `Categories=` 是**空串**，而 freedesktop 要求至少一个主分类，缺了启动器只能把它归到「其他/未分类」，现在连 `Categories=Utility;` 一起断言
- **CI/Desktop**: 桌面壳层的 **Rust 单测在 CI 里此前完全没有覆盖**——`ci.yml` 的回归门禁只跑 `tests/` 下的 vitest，于是「托盘白板」那类只有单测能抓的问题在 CI 全绿的情况下活到了实机验收。四平台矩阵的 `package` job 现在在 gateway 负载与 sidecar staging 之后跑一步 `cargo test --locked`（本机 153 passed；唯一失败的是 `gateway::kills_grandchildren…`，原因是本机沙箱禁止 `ps`，与代码无关）。两个**刻意**不加的开关：不加 `--target`（单测跑宿主三元组，跨架构的 macos-amd64 因此不需要 Rosetta；实测宿主 triple 的 externalBin 缺失不影响编译）、不加 `--release`（`src/shell/selftest.rs` 有两条用例是 `#[cfg(all(test, debug_assertions))]`，release 下会被**静默跳过**——那是「测试在跑，但没跑全」的假绿）
- **Zed/OAuth**: 修「错误密钥的 token 被静默当成有效凭据存下」的真实缺陷——它同时是回归门禁的**概率性假红**（CI 首次跑挂、重跑即绿，`tests/unit/zed-native-auth.test.js :: criterion L` 报 `expected 'done' to be 'error'`）。根因在 `decryptZedAccessToken` 的 PKCS#1 v1.5 兜底分支：v1.5 去填充**没有任何完整性校验**，而 OpenSSL ≥ 3.2 对该路径启用 **implicit rejection**——私钥不匹配时 `privateDecrypt` **根本不抛错**，直接返回随机字节；原先「解出文本不含 U+FFFD 即视为成功」的判据在这堆随机字节上约 **0.8%** 成立（CI 的 Node 22.23.3 / OpenSSL 3.5.8 实测：20000 个错误密钥密文 166 个被接受，长度全落在 0–8 字节，其中还有 `"зO"`、`"gr\u0002"` 这类并非可打印 ASCII 的值）。于是「上一个弹窗留下的密文」会被当成真 token 建出连接。现改为**只接受凭据形状的明文**（≥16 字节、可打印 ASCII 且无空白——真 token 要原样进 `Authorization: <userId> <token>` 头，Zed 自己签发的是 64 字符 base64url，16 是对实测 8 字节垃圾的宽裕余量）；OAEP 路径本身有完整性校验，未改动。修复后同规模复测 **0/20000**。新增 3 条用例：确定性拒绝实测到的垃圾形状、确认合法 V0 token 仍可解（兼容保留）、256 次逐次换密文的错误密钥全部拒绝；变异测试验证过（还原旧逻辑 → 新增用例 2 条立刻失败）
- **Desktop/Windows**: Windows 安装包（`-windows-amd64-installer.exe`）用的是 **NSIS 自带的默认图标**（绿蓝地球），不是应用图标（用户实测截图）。根因是 `tauri.conf.json` 的 `bundle.windows.nsis` 只写了 `installMode`，没写 `installerIcon`——而 Tauri 的 `installer.nsi` 模板里图标是**条件定义**：`!if "${INSTALLERICON}" != ""` → `!define MUI_ICON`，缺省时这个分支不成立，NSIS 就回落到自己的默认图标。已补 `"installerIcon": "icons/icon.ico"`（连带 `uninstallerIcon`，卸载器同理）。用 Tauri 固定的 NSIS 3.11 实测过对照：不设时提取出的图标是 NSIS 默认地球，设成 `icons/icon.ico` 后提取出的是应用图标；也确认了 NSIS 接受这个 6 个尺寸全为 PNG 压缩的 `.ico`
- **Desktop/Windows**: 运行时会多出一个 CMD 窗口（用户实测截图）。根因是壳层 `main.rs` **缺 `windows_subsystem` 声明**：缺了它，release 版被链接成**控制台子系统**程序，Windows 就为它分配一个控制台窗口——标题是 exe 全路径（NSIS `currentUser` 装到 `AppData\Local`，与截图一致），内容正是壳层日志实现打到 stderr 的日志 + `gateway.rs` 转发上来的 sidecar 输出。补上 `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`（Tauri 官方模板同款，且用 `not(debug_assertions)` 门控：debug 构建保持控制台，`tauri dev` / `verify-shell.mjs` 照旧看得到日志）。连带一处：`gateway.rs` 的 `taskkill` 补 `CREATE_NO_WINDOW`——壳层不再有控制台后，控制台程序 `taskkill` 会被 Windows **新分配**一个控制台窗口（启动回收孤儿与退出清理各闪一次黑窗）。两处均用真实二进制实测过：父进程为无控制台的 GUI 程序时，默认创建的子进程 `GetConsoleWindow()` 非零且 `IsWindowVisible` 为真（即黑窗），加 `CREATE_NO_WINDOW` 或 `DETACHED_PROCESS` 后均无控制台
- **语言/首启**: 全新安装后首次打开，界面是英文而不是跟随系统中文（用户实测：Windows 与 MX Linux；macOS 看着正常只是因为升级安装保住了旧的 webview cookie store——**这是三平台共性问题，不是平台差异**）。根因是面板唯一的语言真值源是 cookie `locale`，全新安装没有 cookie 就落到 `DEFAULT_LOCALE = "en"`，而「跟随系统」只在用户**主动点选**时才触发；唯一的自动恢复逻辑挂在 profile 页，首启落点是 `/dashboard`，**永远不经过它**。

  现把语言收敛成一个概念「**应用语言**」，规则为 **显式选择 > 系统语言 > 英文**，由**壳层启动时判定一次**（它是唯一在首启那一刻存在判定源的一层——面板自身没有系统语言来源，网关不读 `Accept-Language`），再经注入脚本写进 cookie 给面板读。面板不再自己判定；优先级链只实现一次，壳层菜单与面板界面因此**不可能出现「菜单中文、面板英文」**。显式选择的权威从 localStorage / cookie / `POST /api/locale` 三处收敛到 `shell-settings.json` 的 `locale` 字段（壳层必须**先于**面板知道语言，cookie 降级为派生态；后两者连同 `localStorage` 一并退役）。

  连带修掉一个已存在的缺陷：面板曾声明支持 **34 种**语言而 `public/i18n/literals/` 下只有 **6 份**字典，选到其余 28 种会 fetch 404 → 异常被吞 → **静默回落全英文**。现集合收窄到 `en` / `zh-CN` / `zh-TW`，**不支持的语言视为「未选择」**（回落系统语言，而不是静默英文），并新增断言把「集合必须等于字典集合」钉死。`<html lang>` 也改为跟随应用语言（此前硬编码 `en`，中文界面上影响 CJK 字形回退与无障碍朗读）。

  验证：`cargo test --locked` **159 passed**（新增「显式选择优先」「无选择用系统语言」「系统语言不受支持回落英文」「`locale` 只接受受支持语言」「能跨写盘往返」等用例）；面板侧新增 `tests/unit/i18n-locale-set.test.js`（10 项），并做变异验证（临时加一个 `xx.json` → 集合一致性断言立刻变红）。

  **已知限制（不是本改动的缺陷）**：Linux GUI 会话若 `LANG=C.UTF-8`，壳层、面板、服务端**三层同源**地都读不到语言信息（`sys-locale` 与 WebKitGTK 的 `navigator.language` 都来自 `LANGUAGE`/`LC_ALL`/`LANG`），首启仍回落英文；出路是用户显式选择一次后由权威存储固化。另：Windows 上 `sys-locale` 是否返回 `zh-Hans-CN` 仅有理论依据，需真机看壳层启动日志的「菜单语言检测」行确认。**首屏仍会先渲染英文再替换**（字典 145 KB，SSR 出英文静态页 → hydrate → fetch → 替换 DOM），消除它需要服务端读 cookie（代价是把 `/dashboard` 从静态预渲染拉成动态渲染，而首启那次仍读不到），属刻意取舍。
- **Desktop/打包**: Windows 安装向导是英文的（中文 Windows 上也是）。根因是 `tauri.conf.json` 的 `bundle.windows.nsis` 没写 `languages`，Tauri 缺省只内置 `["English"]`。现内置 `English` / `SimpChinese` / `TradChinese` 三种，**按系统语言自动匹配**（不插语言选择对话框——需求是跟随系统，不是让用户选）。按既有惯例（用户可见文案一律按字面量钉死，见 `.desktop` 文案那条）补两层断言：构建前的配置级 fail-fast（三种语言齐全 + `displayLanguageSelector` 为假）与 Windows 包烟测的**产物级**检查（读 Tauri 生成的 `installer.nsi`，断言三条 `MUI_LANGUAGE` 存在且 `DISPLAYLANGUAGESELECTOR` 为 `false`）——后者所在目录不在 `pack-artifacts.mjs` 扫描的 `bundle/` 之下，此前从未被任何检查看过。变异验证：删 `languages` / 只留英文 / 插选择对话框，三种变异均被配置级断言判红。
- **Desktop/设置入口**: Windows / Linux 此前只能从**托盘右键菜单**进设置，不方便。现面板顶栏右侧新增**齿轮**入口（三平台一致，浏览器形态同样可用，仅「软件更新」等壳层专有分段不呈现），托盘菜单的「设置…」同时提到**第一位**。之所以不能只靠托盘：Tauri 文档明确 `TrayIconEvent` **在 Linux 上不发射**、`show_menu_on_left_click` **在 Linux 上不支持**——代码里那个「左键单击唤窗」分支在 Linux 上根本不会被触发（已实现但无效），这是上游限制，靠面板内入口兜住。
- **Desktop/设置入口（上一版装了没生效）**: 上一版新增的顶栏设置齿轮，用户实测「装了但没生效」——面板里根本看不到它，且**控制台与网关日志一条报错都没有**。根因不在面板（入口代码是对的），而在 Next 16 的 `.next/server/route-cache`：它是**持久化响应缓存且没有跨构建失效机制**——key 只由 `(kind, sha256(页面模块名), 路径)` 组成（`next/dist/server/lib/route-cache-key.js:61-75`，对 `incremental-cache/**` 搜 `buildId|BUILD_ID|deploymentId` 零命中），条目首次请求时从「种子」（`.next/server/app/<route>.html`）**提升**而来，此后只认这份提升副本（`file-system-cache.js:128` 的种子存在性检查一旦副本已存在就整个跳过），而 `/dashboard` 的 `initialRevalidateSeconds` 是 `false`，连「过期」都不会。于是**覆盖安装**时：上一版运行时写下的旧 HTML 外壳原样留着 → 它引用上一版的 chunk 文件名 → 实测该机 `.next/static/chunks/` 已积累三代 chunk（10-09 / 10-10 / 10-11）**旧 chunk 还在盘上** → 浏览器照旧把上一版界面渲染出来，新入口压根没进 DOM。修法分两层：① **网关入口**（`custom-server.js` 的 `purgeStaleRouteCache`，在 `require(standalone)` 之前调用）按 `.next/BUILD_ID` 判定构建身份变化后清掉缓存；② **打包脚本**（`tools/build-server.mjs`）剔除产物里的 route-cache 并加产物级守卫。判据用 BUILD_ID 是因为「构建变了」正是缓存变错的充要条件；戳记写在**缓存目录内部**（`route-cache/.build-id`）让戳记与它描述的那份缓存同生共死——第一版把戳记放在 `.next/` 根下，而**存量安装恰恰没有戳记**，会漏掉正是要修的那批机器。装机路径不止一条（NSIS 覆盖安装、Tauri updater、手工拷贝、开发期直跑），唯一都被经过的一层是网关入口，故判定放那里；清理是 fail-open 的（清不掉只留日志，绝不让网关起不来），且缓存是纯派生态、清掉不丢任何用户数据。设计留档 `docs/adr/0009-route-cache-invalidation.md`。验证：新增 `tests/unit/route-cache-purge.test.js`（11 项，含接线守卫）并做两次变异验证（把戳记移回缓存目录外 → 6 条立刻红；把清理调用注释掉 → 接线守卫立刻红，且这一步暴露并修掉了守卫自身的假绿：注释掉后子串仍在文件里，`indexOf` 照样通过）；A/B 对照在**真实安装目录副本**上跑同一份负载——旧入口返回的 14 个 chunk 里 4 个是上一版文件名、0 个当前版（FAIL），新入口 0 个旧名、4 个当前版（PASS）；最终用**真浏览器**（Edge headless + CDP，跑 Bun sidecar 与用户真实安装目录）验证：齿轮在真实 DOM 中 `PRESENT`、点击前模态框 `closed`、点击后 `OPEN` 且左栏 5 个分段、标题 `Settings`。本次已就地修复用户机器上的安装（清缓存 + 更新入口，原缓存与入口均已备份）
- **面板/设置入口位置**: 上一版把设置入口做成了**顶栏右上角齿轮**，用户实测反馈「太丑」——顶栏是「当前页」的语境（标题、面包屑、页面级搜索），一个全局设置图标挤在那里既抢注意力、又只是个没有文字的裸图标。现移到**侧边栏底部**，以分隔线与导航列表分开：① 语义正确——导航列表装的是内容路由，设置是全局模态框、不是一条路由，底部单独一块正好表达「它不属于内容导航」；② 可发现性更好——能带**文字标签**（「设置」/「Settings」，走既有字典），而这个入口当初存在的唯一理由就是「Windows/Linux 用户找不到设置」；③ 空间更宽裕——实测品牌行可用内容宽仅 239px、现有品牌链接已占 159px（余量 80px，齿轮需 32px），几乎没有冗余，而底部可占满整个侧边栏宽度；④ 可扩展——以后能继续放「关于」「检查更新」。顶栏齿轮一并移除（不留两个入口）。侧边栏在桌面与移动抽屉**复用同一组件**，故一处改动三平台与窄屏一并生效；窄屏点入口时先收起抽屉（否则关掉模态框后用户面对的是一个仍开着的抽屉）。实现只发既有的 `irouter:open-settings` window 事件，**不新增 IPC 与权限**（对齐 ADR 0008 的「IPC 面最小化」）。验证：真浏览器（Edge headless + CDP）11 项断言全绿——顶栏齿轮已移除、入口在侧边栏底部且带文字标签、占满侧栏宽度、点击后模态框打开且 5 个分段渲染、中文界面下标签为「设置」、900×600 抽屉形态下点入口后抽屉自动收起且模态框正常显示
- **面板/清理**: 删掉 6 个重构遗留的**孤儿组件**（零引用零测试，UI 上点不到）：`HeaderMenu.js`（上游 `Header.js` 曾渲染它，本仓 `4c3a9c0` 的「顶栏精简」摘掉渲染点后成为死代码——此后还给它的 Settings 项补过事件，改的是一直没渲染点的组件）、`ChangelogModal.js`（唯一渲染点在被删的 HeaderMenu 里）、`Avatar.js`、`Footer.js`（landing 页用的是它自己那份）、`HeaderLanguage.js`、`LanguageSwitcher.js`（34 宫格语言选择器，语言集合收窄后语义也不再成立）。连带清理 barrel 导出与一处指向已删组件的注释。
- **Desktop/Windows**: 安装器底部那行（NSIS `BrandingText`，取自 `bundle.copyright` = `tauri.windows.conf.json`）用户实测 `©` 糊成一团。根因：中文向导的 UI 字体由 `SimpChinese.nlf` 决定——实测是**宋体 9pt**（读运行中安装器页脚控件 id 1028 的 `WM_GETFONT` 证实），`©` 在 9pt 下笔画全挤进不到 7px，截图一缩放/重编码最先溃散（DPI 位图拉伸已排除：模板自带 `ManifestDPIAware true` + `ManifestDPIAwareness PerMonitorV2`）。现在不动文案、改页脚渲染：新增 `windows/installer-hooks.nsh` 经 `nsis.installerHooks` 接入，用 MUI2 官方扩展点 `MUI_CUSTOMFUNCTION_GUIINIT` / `UNGUIINIT` 在 GUI 初始化时 ① 把页脚换成 **10pt Segoe UI**；② 把页脚控件（id 1028/1256）**底边不动、向上加高 8px@96dpi**（按 DPI 换算）——只换字体实测会出现新问题：控件高仅 12px（按旧小字体设计），10pt 行高放不下、字底被裁，且下方 2px 处正好压着向导的分隔线（用户看出的「文字下方像被挡住」）。三个坑原型实测过：直接定义 `Function .onGUIInit` 会撞 MUI2（它由 `MUI_LANGUAGE` 宏展开时定义，源码里搜不到）；卸载器侧函数必须带 `un.` 前缀；NSIS 代码里寄存器是 `$3`、`$r3` 只在 System::Call 字符串里有效（写错会把控件算成 0×0）。两层断言：配置级 fail-fast（`installerHooks` 必须设置且文件存在）+ Windows 包烟测产物级（生成的 `installer.nsi` 必须含 `installer-hooks.nsh` 的 include）——都是「删掉后构建照常、只有这道会红」的守卫。验证：`tauri build --target x86_64-pc-windows-msvc --bundles nsis` 重打包；实机读控件字体 = Segoe UI、控件被加高为 20px；对截屏做**逐行像素分析**：文字墨迹止于分隔线上方 1px、且完整无裁切。
